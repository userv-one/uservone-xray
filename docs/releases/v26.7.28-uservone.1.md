# v26.7.28-uservone.1

Minimal uservone patch on top of the production-proven Xray-core v26.7.28 baseline. The release provides one Xray artifact for VLESS+Reality, Shadowsocks 2022, and SOCKS5.

## Baseline and compatibility

- Upstream tag: `v26.7.28`
- Upstream commit: `5ca6f4b7d4dc20a881d4330e498892697627ec0c`
- Fork patch: `uservone-keepalive.1`
- Release assets: `uservone-xray-26728-linux-amd64`, `uservone-xray-26728-linux-arm64`, `SHA256SUMS`, `buildinfo.json`, and `sbom.spdx.json`

No VLESS, REALITY, XTLS Vision, Shadowsocks 2022, or SOCKS5 wire-format files are changed. REALITY `minClientVer`, uTLS fingerprints, subscription formats, and credential derivation are unchanged. The text version banner still starts with `Xray 26.7.28`.

There are no expected breaking changes for current uservone-platform configurations. For other deployments, note that missing or unknown SOCKS `auth` is now rejected instead of enabling implicit `noauth`, and `password` requires an account.

## Socket defaults and overrides

Inbound and outbound TCP keepalive defaults are 60 seconds idle and 15 seconds between probes. Existing platform values `20/15/4` override these defaults, so the effective node configuration remains `tcpKeepAliveIdle=20`, `tcpKeepAliveInterval=15`, and `tcpKeepAliveCount=4`.

## uservone-platform migration

1. Set the release pin to `v26.7.28-uservone.1` and select `uservone-xray-26728-linux-<arch>` by node architecture. Verify each download against the release `SHA256SUMS` before installation.
2. Introduce `XRAY_IMPL=uservone-legacy` (or an equivalent explicit pin flag) so upstream and uservone installation paths cannot be confused.
3. Update `server/ssh.js`: replace the official-only installer with the uservone release installer, preserve the previous binary/config, and switch only after `xray run -test` succeeds.
4. Update `server/nodeHealth.js` / `collectNodeFingerprint` to consume `xray version-json` instead of parsing the first text banner line. Use `version`, `upstream_commit`, `fork`, and `build` for drift reporting.
5. Refresh `drift_baseline` from the release `buildinfo.json` after the canary is verified. Do not refresh it before the rollout decision.
6. Update `server/.env.example`, protocol stability tests, and diagnostics to expect `uservone-keepalive.1` and machine-readable version data.
7. Preserve `deriveSocks5Credentials`, subscription URI formats, the explicit SOCKS `auth: password` configuration, and the independent health keys `shadowsocks:tcp:8388` and `shadowsocks:udp:8388`. A UDP probe failure must not automatically revoke the TCP path.
8. `GET /api/account/telegram-proxies` must continue returning `host`, `port`, `username`, `password`, and `deepLink` with existing semantics.

## Canary and rollout

Deploy to one canary node only, then run the platform protocol probe and A/B client checks. Required client coverage includes sing-box 1.14.2, sing-box 1.14.4, Throne, Happ, and v2rayNG. The loopback acceptance test for both sing-box versions must return HTTP 204 with identical upstream/fork results.

**Do not enable this release fleet-wide before canary + sing-box/Throne compatibility checks pass.** Any `reality verification failed` or `tls_handshake_failed` result blocks rollout. No production-node installation is performed by the release workflow.

## Rollback

Before installation:

```bash
sudo install -m 0755 /usr/local/bin/xray /usr/local/bin/xray.previous
sudo cp -a /usr/local/etc/xray/config.json /usr/local/etc/xray/config.json.previous
```

Install only after validation:

```bash
./xray run -test -config /usr/local/etc/xray/config.json
```

To roll back:

```bash
sudo systemctl stop xray
sudo install -m 0755 /usr/local/bin/xray.previous /usr/local/bin/xray
sudo cp -a /usr/local/etc/xray/config.json.previous /usr/local/etc/xray/config.json
/usr/local/bin/xray run -test -config /usr/local/etc/xray/config.json && sudo systemctl start xray
```

## Verification report

Required checks are the full Go test suite with verified geodata, `go vet ./...`, targeted protocol tests, configuration preflight, `version-json`, legacy banner validation, Linux cross-builds, checksum verification, and independent A/B loopback tests. Race checks require a CGO-enabled environment with a C compiler and are reported separately when unavailable.

External production nodes are never contacted by the release workflow.
